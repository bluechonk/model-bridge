# Phase 3 · 格式分析（Format Analysis）

> **实现语言（2026-10-07）**：本阶段现由 Python 实现 —— `src/catpaw_bridge/analyze.py`，
> 命令行入口 `uv run catpaw-analyze`。下文原始输出来自 TS/Node 版脚本（tag `v0.3.0-ts`）；
> 结论与证据等级不变，详见 [../README.md](../PROTOCOL.md)。

## 目标

把 Phase 2 选出的唯一主目标字段 `ssoTokenEnc` 当成一个黑盒字节串来量，回答三个可证伪的问题：base64 解码后到底是多少字节？按 IV 12 + tag 16 切分是否自洽、三段各多长？这段数据是明文/压缩，还是密文？

本阶段**不**判定算法归属：它只产出"长度 + 统计特征 + 首字节结构"这三类证据，用来印证一个由代码给出的切分假设；算法名与常量归 Phase 4。

## 方法与命令

执行命令：

```text
npm run analyze        # 等价于 node scripts/analyze-token-blob.ts
```

入口 `scripts/analyze-token-blob.ts`：`readEncryptedSsoToken()`（只从 `catx-credential.json` 取出 `ssoTokenEnc` 字符串，不解密）→ `analyzeEncodedBlob()` → `formatBlobAnalysis()`（`src/phase3-format-analysis/index.ts`）。

本阶段是纯计算，无解密、无网络、无写盘 `[代码]`：

| 指标 | 实现 | 说明 |
| --- | --- | --- |
| 解码字节数 | `decodeBase64()` = `Buffer.from(encoded, 'base64')` | 只解码、不验签 |
| 三段切分 | `bytes.subarray(0, 12)` / `[12, 28)` / `[28, …)` | 切分常量来自 `DEFAULT_BLOB_LAYOUT` |
| 熵 | `shannonEntropy()`：256 桶字节频率的香农熵（bit/byte，最大 8） | 经验估计，短样本天然偏低 |
| 可打印占比 | `printableRatio()`：0x20–0x7e 的字节占比 | — |
| 是否像明文 JSON | `looksLikeJson`：看**整个解码结果**的首字节是否为 `{` / `[` / `"` | 见「踩坑与修正」第 1、2 条 |
| 指纹 | `fingerprintBytes()`：sha256 前 16 位 hex（`src/utils/redact.ts`） | 只用于跨次运行比对同一密文，不可逆 |

**关于切分 12/16 的来源（关键）**：这两个数不是本阶段从长度分布或熵里试出来的，而是 **Phase 4 在 `app.asar` 里读到实现常量后给本阶段的输入**。`DEFAULT_BLOB_LAYOUT` 的注释写明："实测常量：`crypto.createCipheriv('aes-256-gcm', key, iv)` 用 12 字节 nonce，结尾 `getAuthTag()` 默认 16 字节"，并且接口注释直接标注为"由 Phase 4 的代码证据确定的字节切分" `[代码]`。Phase 3 的作用只有一个：用 `12 + 16 + 199 = 227` 与密文的统计特征去**印证**这个切分自洽，而不是反过来猜算法。

本次运行的原始输出留存于 `.tmp\runlogs\analyze-token-blob.txt`，下面「原始输出」一节的内容全部取自该文件。

## 结论

1. `ssoTokenEnc` 的 base64 长度 **304**（含填充 `=`），解码后 **227 字节** `[实测]`。两者自洽：227 = 75×3 + 2，编码为 75 组 4 字符 + 1 组"2 字节 → 3 字符 + 1 个 `=`" = 304 字符 `[推断]`。
2. 按 IV 12 + tag 16 切分，剩余密文 **199 字节**，且 12 + 16 + 199 = 227 与解码字节数完全吻合 `[实测]`。
3. IV（hex）`5007e731cea21e102988f0ef`：24 个 hex 字符 = 12 字节，与切分长度自洽 `[实测]`。IV 不是秘密，可以打印。
4. auth tag 前 8 字节 `a5d92fb1fb9774ca` `[实测]`；只输出前 8 字节，够做跨次比对、不足以还原 tag。
5. 密文段香农熵 **6.9466 bit/byte**（结论串中按 3 位小数写作 6.947）`[实测]`。
6. 密文段可打印 ASCII（0x20–0x7e）占比 **37.7%** `[实测]`。
7. `looksLikeJson = false` `[实测]`：整个解码结果的首字节是 IV 的第一个字节 `0x50`（ASCII `P`），不是 `{` / `[` / `"`；即该字段不是"根本没加密的明文 JSON" `[代码]`。
8. 密文指纹 `426ad1043b8f8e73`（sha256 前 16 位）`[实测]`，只用于确认"两次读到的是同一段密文"，不可逆推到原文 `[代码]`。
9. 判定：**非明文结构**；结合 Phase 4 的实现常量，该 blob 判定为 **AES-256-GCM 密文** `[实测]`+`[推断]`。严格说本阶段自己证明的是"不是明文、且 12/16 切分自洽"，"是 AES-256-GCM"这一步由 Phase 4 的代码证据支撑 `[代码]`。
10. 密文长度 199 字节与后续确认的 token 长度属同一量级：token 的脱敏形态为 `AgEKJlOd…[152]`，若明文是 `{"access_token":"<152 字符>", …}` 这类小 JSON 信封，整体可落在 199 字节内 `[推断]`（明文的确切形状由 Phase 6 定论，本阶段不做断言）。

### 为什么熵只有 6.95，而不是接近 8

- 香农熵是按**观测到的字节频率**估出来的经验值，属于有偏估计：样本越短越偏低。n 个样本最多只能出现 n 种不同的字节值，因此经验熵的上限就是 `log2(n)`。本密文 n = 199，`log2(199) ≈ 7.64 bit/byte`——6.9466 已经是在"最多 199 种取值"这个天花板下很高的读数 `[推断]`。
- 反过来看，只有样本足够长时才能读到接近 8 的值：同一个 `shannonEntropy()` 作用在 4096 字节随机输入上才会给出 `> 7.5` 的读数 `[代码]`（`src/phase3-format-analysis/index.ts` 的熵实现）。
- 所以 **"熵 < 7.5" 不能当作"没加密"的证据**。本阶段真正可用的是两个判据：一是 `looksLikeJson`（首字节结构），二是 12/16/199 的长度自洽性；算法归属一律以 Phase 4 的代码常量为准。
- 可打印占比同样可以交叉核对：均匀随机字节落在 0x20–0x7e 的概率是 95/256 ≈ 37.1%，实测 37.7% 与之基本重合，符合随机密文的期望，而不像文本 `[推断]`。

## 踩坑与修正

1. **`looksLikeJson` 的判定位置被修正过（本阶段主要的一个坑）。** 最初检查的是**密文段**的首字节（`ciphertext[0]`），后来改为检查**整个解码结果**的首字节（`bytes[0]`）。理由：真信封的第一个字节是随机 IV 的首字节，命中的 `{` / `[` / `"` 概率只有 3/256 ≈ 1.2%；而"这个字段根本没加密"的情形下，整个字段会直接以 JSON 的开头字符起头。改判位置后，这个布尔值才真正对应它要回答的问题——"该字段到底有没有加密" `[代码]`（见 `src/phase3-format-analysis/index.ts` 中"判定…要看**整个**解码结果的首字节"这段注释与紧随其后的实现）。
2. **修正没有一次清干净：文案曾指向旧判据（已修）。** 改判位置之后，两处文字一度还沿用旧描述——字段注释写"密文段是否以 `{` 开头（明文才会）"，`verdict` 的分支文案写"密文段像明文 JSON ⇒ 该字段可能未加密"。实现看的是整串首字节、文案说的是密文段，两者不一致；只读文案的人会误判判据。**已把这两处一并改成"整个解码结果的首字节"与"整个字段像明文 JSON"**，`src/phase3-format-analysis/index.ts` 的注释与分支文案现与实现一致 `[代码]`。
3. **12/16 的因果方向必须写清，否则本阶段看起来像在猜算法。** 切分是 Phase 4 从代码里读到的常量（`DEFAULT_BLOB_LAYOUT`），Phase 3 只是验证"长度切得通、统计特征不像明文"。RUN-LOG 若省略这一句，就会把"代码常量"误读成"由熵推断的结论" `[代码]`。
4. **不能只看结论串里有没有 `AES-256-GCM` 就判断熵有多高。** `entropy > 7.5` 的分支文案是"高熵且非明文结构 ⇒ AES-256-GCM 密文特征明显"，本机短密文走的是 else 分支（"…短密文的熵估计天然偏低，结合 Phase 4 的实现证据判定为 AES-256-GCM 密文"）。两条分支的输出里都含 `AES-256-GCM` 字样，所以必须读"密文熵"那一行的数值才能知道实际走了哪个分支；本机走的是 else 分支 `[实测]`+`[代码]`。
